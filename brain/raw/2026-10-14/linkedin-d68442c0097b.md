Why is software architecture treated so differently from physical engineering?

When designing hardware or a house, every detail is mapped out on precise blueprints. When you renovate years later, you base your decisions on exact structural plans.

In software?

Someone draws a high-level box-and-arrow diagram in a generic drawing tool, the code gets written, and every future change requires reverse-engineering the system all over again—from high-level business logic down to specific code behavior.

I’m not generalizing, but this pattern is everywhere. Why do we often skip formal modeling?

1️⃣ Budget&Time: Modeling is seen as an unnecessary cost, so it’s the first thing cut when scope or deadlines shrink.
2️⃣ Skill Gap: Teams know how to gather requirements, design high-level architecture, and write code—but formal modeling is a lost skill.
3️⃣ It’s Boring: Nobody enjoys manually keeping documentation in sync with code after the initial excitement wears off.
4️⃣ Software is Fluid: A house is built once; software evolves daily. Updating blueprints after every single change is far more frequent—and far more painful—than in hardware or construction.
5️⃣ Because We Can: Without blueprints, a house collapses and hardware fails. Software will still run even though, without documentation, its a black box unless you dig straight into the source code

As Michael Roy highlights in his article (https://lnkd.in/dzZ4t2kG), this isn't just about losing technical software architecture. It’s also about losing the core WHY decisions behind the project—the original intent, business tradeoffs, and key choices that simply evaporate once the initial phase ends or the team moves on.
