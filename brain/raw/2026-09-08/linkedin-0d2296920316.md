IncidentIQ — Part 1: Rethinking the Architecture
 
When I started building IncidentIQ, the goal was simple:
Can AI help investigate an incident and identify its probable root cause?
 
I built a working prototype around that idea:
Incident → Planner → Log Agent → Metrics Agent → Deployment Agent → RCA → Report
 
For a proof of concept, this approach worked.
 
But while thinking about taking IncidentIQ beyond a demo, I started looking at the problem differently.
 
What would happen during a real production incident?
 
An incident doesn't always stay within one layer.
 
A latency spike could be caused by the application, database, deployment, API traffic, infrastructure, or even a security issue.
And in a real environment, investigating this could mean checking multiple systems and manually connecting evidence from each one.
 
That's when I realized:
The challenge isn't just the AI agent. It's the system around it.
 
I started thinking about questions like:
 → How should the system decide what to investigate next?
 → How can new data sources be added easily?
 → How do we handle large volumes of logs and metrics?
 → What happens when a source is unavailable?
 → How do we design for security, failures, scalability and traceability?
 
So I'm now rethinking IncidentIQ around a single Investigation Agent / Orchestrator.
 
Instead of following a fixed sequence, the investigation should work more like:
Incident → Collect Evidence → Reason → Decide What to Check Next → Repeat
 
Logs, metrics, deployments, APIs, databases, infrastructure, security and historical incidents become tools available to the investigation.
 
The goal is also changing.
 
Not just:
"Here is the root cause."
 
But:
Root Cause + Evidence + Timeline + Confidence + Actions + Remediation + Prevention
 
I'm currently exploring the system-design side of this redesign before implementing it.
 
For me, this is the interesting part of building IncidentIQ now — taking something that works as a prototype and figuring out what it actually needs to become a production-oriented system.
 
A special thanks to Rajat Kumar Sahu for the discussion and feedback that pushed me to look beyond the AI-agent layer and think more deeply about the system design behind IncidentIQ.
 
Part 1 of the redesign journey.
