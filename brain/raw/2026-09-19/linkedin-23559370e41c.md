We had 300+ Playwright tests.
The tests were good.
The framework was stable.
The automation coverage was growing.
But there was one problem:
Our CI pipeline was becoming too slow to be useful.
A developer would raise a PR, and then wait 20+ minutes just to get automation feedback.
Eventually, people started thinking:
"I'll check the pipeline later."
That's when I realized something important as an SDET:
Writing automation is only half the job.
Making automation fast enough to be part of the development workflow is the other half.
So we changed the pipeline.
~ 1. Parallel execution with sharding
Instead of running 300 tests sequentially, we split the suite across multiple GitHub Actions runners using Playwright's --shard capability.
~ 2. Browser caching
We cached Playwright browser binaries instead of downloading them on every CI run.
~ 3. Combined reporting
Each shard generated its own results, so we merged the reports into a single report that the team could easily understand.
We also added two small but important safeguards:
--forbid-only → prevents accidental .only tests from reaching the main branch.
fail-fast: false → allows other shards to complete even when one shard fails, giving the team a complete picture of the run.
The result?

Before:
300 tests → ~22 minutes

After:
300 tests + 4 shards + caching → ~4 minutes
That wasn't just a performance improvement.
It changed how the team used automation.
Developers started getting feedback much earlier.
Failures became part of the PR workflow instead of something checked later.
And automation became a quality gate, not just a collection of test scripts.
That's the difference I've learned between writing automation and engineering an automation system.
A Senior SDET shouldn't only ask:
"Can we automate this?"
The better questions are:
"How fast will it run?"
"How will it scale?"
"How will it behave in CI?"
"How will developers consume the results?"
"What happens when the suite grows from 300 to 3,000 tests?"
Because eventually, your test suite can become the bottleneck.
And when that happens, writing more tests isn't always the answer.
Engineering the pipeline is. 🚀
